# 이슈 정규화 규격 (단일 원본)

기획을 **구현 가능한 이슈 트리**로 분해할 때의 정규 규격. `ib-issues`(단독)와 `ib-generate`
4단계, `ib-progress`가 이 규격을 공유한다.

## 트리 구조 (2단계)

- **에픽(부모 이슈, `type="epic"`)**: 기획서의 어느 섹션에서 나오는지는 아래
  "기획서 어디에서 이슈가 나오는가" 표를 따른다.
- **작업 이슈(하위, `type="task"`)**: 각 에픽을 실제 착수 가능한 단위로 쪼갠다.
  규모 기준 하나당 **반나절~2일**. 너무 크면 더 쪼개고, 너무 잘면 합친다.

## 기획서 어디에서 이슈가 나오는가 (🔴 누락 방지)

기획서의 **기능 표만 보면 성능·보안·접근성 작업이 통째로 빠진다.** 아래 대응을 지켜라.

| 기획서 섹션 | 이슈로 어떻게 |
| --- | --- |
| `## 4. 핵심 기능` | **각 행 = 에픽 하나.** 기본 골격. |
| `## 6. 비기능 요구사항` | **각 항목 = 이슈 하나.** 특정 기능에 속하면 그 에픽의 태스크로, 제품 전반이면 `[Infra]`·`[Security]` 같은 **별도 에픽**을 만들어 그 아래 둔다. 기준값(응답시간·동시접속 등)을 **완료 조건에 숫자로** 옮긴다. |
| `## 8. 테스트 시나리오` | 새 이슈를 만들지 말고, **그 시나리오가 커버하는 에픽의 완료 조건**에 인수 조건으로 녹인다. E2E 검증 자체가 작업이면 `[QA]` 태스크로 뺀다. |
| `## 5. 범위 밖` | **이슈를 만들지 마라.** 이번 버전에서 하지 않기로 한 것들이다. |
| `## 9. 핵심 가정 / 미결` | 확정이 필요한 미결이 착수를 막으면 `[Spike]` 조사 태스크로 만든다. 단순 가정은 이슈로 만들지 않는다. |

## 제목 — `[영역] 동사구`

- **영역**: 기능/도메인 축약 태그. 같은 영역끼리 묶이도록 **일관되게** 쓴다 (예: `Auth`,
  `Onboarding`, `Room`, `Race`, `Infra`). 한 프로젝트 안에서 표기를 통일하라(같은 대상에
  `Auth`/`인증`을 섞지 말 것).
- **동사구**: 무엇을 하는지 간결하게 (예: `소셜 로그인`, `방 생성`, `실시간 순위 계산`).
- 에픽이라고 `[에픽]`을 붙이지 마라 — 에픽/태스크 구분은 `type`이 담당한다.

## body — 에픽 (`type="epic"`)

```
{한 줄 요약 — 이 에픽이 달성하는 것}

## 범위
- {포함하는 하위 작업/영역}

## 완료 조건
- [ ] {에픽 수준에서 검증 가능한 조건}
```

## body — 태스크 (`type="task"`)

```
{한 줄 요약 — 무엇을 만들/바꾸는가}

## 작업 내용
- {구체적인 작업 항목}

## 완료 조건
- [ ] {검증 가능한 acceptance criteria}
```

## 공통 규칙

- 🔴 **완료 조건은 반드시 `- [ ]` 체크박스** — 이유·상세는 [conventions.md](conventions.md).
- 섹션 헤딩과 순서를 위 템플릿 그대로 지킨다. 첫 줄은 항상 한 줄 요약(헤딩 없이).
- **연관(기획·화면·도메인)은 body에 글로 적지 말고, 아래 "연동"의 구조적 링크로만 연결한다.**
  대시보드가 "기획 보기/화면 보기/도메인 보기" 버튼으로 렌더하므로, body에 중복하면 staleness만 생긴다.
- **`value`(가치)·`effort`(노력)로 평가** — **우선순위는 이 둘에서 자동 산출**되므로 `priority`를
  직접 넣지 마라.
  - `value`: 사용자/제품 가치. 핵심 유스케이스에 필수면 `high`, 보조면 `medium`, nice-to-have면 `low`.
  - `effort`: 구현 노력/복잡도. 크면 `high`, 보통 `medium`, 작으면 `low`.
  - 산출 규칙(참고): 高가치·低노력=높음, 高가치·高노력=보통, 低가치·高노력=낮음.
- `labels`: 아래 "포지션 분리"의 포지션 라벨을 붙인다. 그 밖의 태그는 꼭 필요할 때만
  — 과하지 않게. (이슈 키 `CH-12`와는 별개 개념 — 키는 자동 부여, 라벨은 자유 태그.)

## 포지션 분리 (🔴 태스크 필수)

**하나의 태스크에 프론트와 백 작업을 섞지 마라.** 섞이면 담당자가 갈리고, 둘 중 하나만 끝나도
완료로 보이며, API 계약을 어디서 정하는지가 흐려진다. 섞였으면 **두 태스크로 쪼갠다.**

포지션 라벨은 **`front` · `back` 딱 두 가지**다. 포지션을 뜻하면서 다른 표기(`frontend`·`fe`·
`web` 등)를 쓰지 마라 — 대시보드 포지션 필터가 이 두 값만 본다.

**이 두 값 외의 라벨은 포지션 축이 아니다.** 도메인 개념을 담은 라벨(`position`=직책, `role`,
`org` 등)이 이름이 비슷해 보여도 그대로 둔다 — 포지션 라벨로 바꾸지 마라.

| 대상 | 라벨 |
| --- | --- |
| **태스크** (`type="task"`) | `front` 또는 `back` **중 하나를 반드시** 붙인다 |
| **에픽** (`type="epic"`) | 양쪽을 아우르므로 **붙이지 않는다** |
| 어느 쪽도 아닌 작업 | `infra` · `qa` · `spike` · `design` 중 해당하는 것 (포지션 라벨 없이) |

- 쪼갤 때는 **계약을 먼저 세운다** — `back` 태스크의 완료 조건에 응답 형태를, `front` 태스크의
  완료 조건에 그 응답을 화면에 어떻게 쓰는지를 적는다. 예: `[Room] 방 목록 API`(back) +
  `[Room] 방 목록 화면`(front).
- `front` 태스크는 대체로 `screenId`를 갖고, `back` 태스크는 대체로 `domainId`를 갖는다.
  없으면 정말 없는 것인지 다시 본다.
- **제목의 `[영역]`과 혼동하지 마라.** 제목 태그는 *기능* 축(`[Auth]`·`[Room]`), 라벨은 *포지션*
  축(`front`/`back`)이다. 제목에 `[Front]`처럼 쓰지 마라.
- 프로젝트가 한쪽만 있으면(예: 백엔드 전용 서비스) 그 라벨만 쓰면 된다 — 억지로 나누지 마라.

## 연동 (구조적 링크)

각 이슈를 만들 때 파생 출처를 **구조적으로 연결**한다:

- `planId`: 파생된 기획의 id — **필수**. 보통 모든 이슈가 같은 기획을 가리킨다.
  🔴 기획이 연결되지 않은 이슈는 **착수(`in_progress`)·완료(`done`) 전이를 서버가 거부**한다
  (기획 확정 가드는 예외가 없다). 작업 중 발견한 이슈를 급히 등록할 때도 반드시 채운다.
- `screenId`: 이슈가 다루는 화면이 있으면 와이어프레임의 해당 `data-screen` id (예: `race-detail`).
  **쓸 수 있는 값은 와이어프레임 응답의 `screens` 목록뿐**이고, 없는 id를 넣으면 서버가 거부한다
  (name별 최신 버전 기준). UI와 무관한 이슈(인프라·백엔드)면 생략.
- `domainId`: 이슈가 특정 도메인(엔티티/테이블)을 다루면 그 도메인 id. 무관하면 생략.
- `applicationId`: 이슈가 속한 앱 id — **필수**. 자세한 규칙과 **이슈 키(`CH-12`)**는
  [application-model.md](application-model.md).

## 적재 순서 (중요)

1. **에픽을 먼저 생성**: `create_issue(projectId, title, body, type="epic", value, effort,
   labels, planId, screenId?, domainId?, applicationId)`. 반환된 각 에픽의 `id`·`key`를 기억한다.
2. **하위 이슈**를 생성하며 `type="task"`, `parentId`에 해당 에픽의 id(cuid) 또는 키(`CH-1`)를 넣고
   `planId`·`screenId`·`domainId`·`applicationId`를 채운다.
