너는 이 프로젝트의 개발자다. 지금까지의 작업을 근거로 **이슈의 완료 조건 체크박스와 상태를
실제 진행도에 맞게 동기화**한다. 대시보드에서 사람이 체크하는 것과 같은 편집을 대신 하는 것이다.
하위 이슈의 상태가 바뀌면 **상위 이슈(에픽)의 상태도 하위에 맞춰 함께 재조정**한다.

> 완료 조건 체크박스 규칙(`- [ ]` GFM)은 [ib-shared/conventions.md](../ib-shared/conventions.md),
> 이슈 규격(에픽/작업 2단계 트리)은 [issue-spec.md](../ib-shared/issue-spec.md).

## 대상

$ARGUMENTS

(비어 있으면: 최근 대화/작업 맥락에서 지금 진행 중인 이슈를 추정하고, 애매하면 물어라.)

## 진행 순서

### 1) 이슈 찾기 · 읽기

- 이슈 키(`CH-12`)나 id가 있으면 `get_issue(issueId=<키 또는 cuid>)`로 읽는다.
- 없으면 `get_project_context(repoPath=<cwd 절대경로>)`(또는 `list_issues`)로 목록을 받아
  대상 이슈를 찾는다(키/제목/맥락 매칭). 없으면 물어라.
- **트리 파악**: 4)에서 상위로 전파하려면 형제 이슈의 상태가 필요하다. 대상 이슈에 `parentId`가
  있으면 `get_project_context`(또는 `list_issues`)로 **프로젝트 이슈 목록 전체를 한 번 받아 둔다**
  — 응답의 각 이슈에 `parentId`·`status`·`key`·`type`이 들어 있어 트리를 그대로 재구성할 수 있다.

### 2) 완료 조건 대조

본문의 "완료 조건" 체크리스트(`- [ ]`/`- [x]`)를 하나씩 본다. **실제 코드/작업 결과를 근거로**
각 항목이 끝났는지 판단한다.

- 끝난 항목: `- [ ]` → `- [x]`
- 아직인 항목: 그대로 (근거 없이 체크하지 마라)
- **추측으로 체크하지 말 것.** 실제로 구현/검증된 것만.

### 3) 저장 (대상 이슈)

- 본문을 수정했으면 `update_issue(issueId, body=<수정본 전체>)`로 저장한다.
  **완료 조건 체크박스 외 다른 본문은 건드리지 마라.**
- 진행도에 맞춰 상태 조정:
  - 일부라도 착수됐는데 `todo`면 → `update_issue_status(issueId, "in_progress")`
  - 완료 조건이 **전부 체크**되면 → 모두 `- [x]` 확인 후 `update_issue_status(issueId, "done")`
  - 막혔으면 → `"blocked"`

### 4) 상위 이슈로 전파 (🔴 상태를 바꿨으면 필수)

3)에서 대상 이슈의 상태를 바꿨고 그 이슈에 `parentId`가 있으면, **상위 이슈의 상태도 하위
전체에 맞춰 재조정**한다. 상위(에픽)의 상태는 사람이 따로 관리하는 값이 아니라 **하위에서
산출되는 값**이다.

> **상태 전이 자체는 서버가 자동으로 한다.** `update_issue_status`가 호출되면 서버가 부모부터
> 루트까지 아래 b의 판정을 그대로 적용한다 — 그래서 대개 네가 상위에 `update_issue_status`를
> 따로 부를 일은 없다. 다만 **서버가 하지 않는 두 가지가 네 몫**이다:
> ① 상위 본문의 **완료 조건 체크박스**(c) — 서버는 본문을 건드리지 않는다,
> ② 결과 **확인과 보고**(5). 상위를 `get_issue`로 다시 읽어 실제로 어떻게 바뀌었는지 확인하고,
> 판정과 다르면(예: 기획 미확정으로 롤업이 건너뛰어짐) 그 사실을 보고에 남겨라.

**a. 하위 상태 모으기** — 1)에서 받아 둔 이슈 목록에서 `parentId === <상위 이슈 id>` 인 이슈를
전부 모은다. 방금 3)에서 바꾼 값을 반영해서 센다(응답이 옛 상태일 수 있으니 내가 전이시킨
값을 쓴다).

**b. 상위의 목표 상태 판정** — 위에서부터 **처음 맞는 줄 하나만** 적용한다.

| # | 하위 이슈들의 상태 | 상위의 목표 상태 |
| --- | --- | --- |
| 1 | **전부 `done`** | `done` (단 c의 확인을 통과해야 함) |
| 2 | 전부 `todo` | **변경 없음** |
| 3 | 그 밖의 모든 경우 (일부만 done, `in_progress`·`blocked` 섞임 등) | `in_progress` |

즉 **하나라도 시작됐으면 상위는 `in_progress`, 전부 끝났을 때만 상위도 `done`** 이다.
`blocked`인 하위가 하나라도 있으면 1번에 걸리지 않으므로 상위는 `done`이 되지 않는다.

- 목표 상태가 **이미 현재 상태와 같으면 호출하지 않는다** (불필요한 전이 금지).
- **되돌리기도 한다**: 상위가 이미 `done`인데 하위에 미완(`todo`/`in_progress`/`blocked`)이
  생겼으면 상위를 `in_progress`로 되돌린다.
- 상위를 `blocked`로 자동 전이하지는 마라 — blocked는 사람의 판단이다.

**c. 상위를 `done`으로 올리기 전 확인** — 상위 이슈를 `get_issue`로 읽어 본문의 완료 조건을 본다.

- 하위 완료로 실제 충족된 항목은 `- [x]`로 바꿔 `update_issue(상위, body=<수정본>)`로 저장한다.
- 상위에만 있는 고유 완료 조건(예: 통합 검증·문서화)이 **아직 안 끝났으면 `done`으로 올리지
  말고 `in_progress`로 두고**, 무엇이 남았는지 보고에 적는다. 하위가 다 끝났다는 사실만으로
  근거 없이 체크하지 마라 — 2)의 원칙은 상위에도 똑같이 적용된다.

**d. 확인** — 상위를 `get_issue`로 읽어 목표 상태가 됐는지 본다. 서버 롤업이 이미 반영했으면
그대로 두고(중복 호출 불필요), 아직 목표와 다르면 `update_issue_status(<상위 키 또는 id>,
<목표 상태>)`로 맞춘다. c에서 상위 고유 완료 조건이 남았다고 판단했는데 서버가 이미 `done`으로
올렸다면, 억지로 되돌리지 말고 **무엇이 남았는지 보고에 적어** 사람이 판단하게 하라.

**e. 반복** — 루트까지 a~d를 반복한다. 서버 롤업도 루트까지 올라가므로 보통은 확인만으로
끝난다. (이슈 트리는 보통 에픽→작업 2단계다.)

### 5) 보고

체크한 항목 / 남은 항목 / 최종 상태를 이슈 **키(`CH-12`)와 함께** 요약한다.
상위 이슈의 상태를 함께 바꿨으면 **무엇을 근거로 바뀌었는지**(예: "하위 4개가 모두 done →
`CH-1`(에픽) done") 한 줄로 덧붙인다. 상위를 올리지 **않은** 경우에도 이유를 적는다
(예: "`CH-1`은 하위 `CH-5`가 아직 todo라 in_progress 유지").

## 주의

- 근거 없는 체크·상태 변경 금지. **실제 작업 결과에만** 근거한다.
- 완료 조건 체크리스트와 상태 외의 것은 수정하지 마라 (제목·우선순위 등은 손대지 않음).
- **상위 이슈의 상태는 하위에서 산출한다.** 하위 근거 없이 에픽만 따로 done으로 올리지 마라.
- **기획 확정 가드**: 이슈의 기획이 `approved`가 아니면 `in_progress`/`done` 전이를 서버가
  거부한다. 거부되면 상태를 억지로 바꾸려 하지 말고, "기획이 아직 확정되지 않았습니다"라고
  사용자에게 알려라 (기획 확정이 선행돼야 개발·진척이 반영된다).
  **상위 이슈도 같은 가드를 받는다** — 하위는 다 끝났는데 상위 전이가 거부되면, 상위 이슈의
  기획이 미확정이거나 연결되지 않은 것이니 그 사실을 보고에 남긴다.
