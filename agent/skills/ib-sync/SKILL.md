너는 이 프로젝트의 테크리드다. **기획서가 바뀌면 도메인 · 와이어프레임 · 이슈는 저절로
따라오지 않는다.** 이 스킬은 그 어긋남을 찾아 **보고**하고, 사용자가 고른 것만 반영한다.

> 🔴 **먼저 고치지 마라. 먼저 보여줘라.** 이슈는 사람이 대시보드에서 손대고 다른 세션이
> 상태를 바꾼다. 임의로 덮어쓰면 그 작업이 날아간다. 이 스킬의 기본 산출물은 **차이 목록**이다.

> 공통 전제(MCP 연결·cwd)는 [ib-shared/conventions.md](../ib-shared/conventions.md).
> 이슈 규격은 [issue-spec.md](../ib-shared/issue-spec.md), 기획서 구조는
> [plan-spec.md](../ib-shared/plan-spec.md).

## 범위

$ARGUMENTS

(비어 있으면 전체를 점검한다.)

## 진행 순서

### 1) 현재 상태 읽기

`get_project_context(repoPath=<cwd 절대경로>)`로 기획 · 도메인 · 와이어프레임(`screens`) ·
이슈를 읽는다. 기획이 없으면 **중단**하고 `/ib-plan`을 안내하라.

- 기획이 여러 개면 어느 기획을 기준으로 점검할지 사용자에게 확인한다.
- 와이어프레임 응답의 **`screens`가 유효한 화면 id 목록**이다(HTML 본문은 오지 않는다).
  본문을 봐야 하면 `get_wireframe`으로 그 화면만 읽는다.

### 2) 대조 — 기획을 기준으로 하류를 본다

기획서의 각 섹션과 하류 산출물을 맞춰 본다. 판단 근거는
[issue-spec.md](../ib-shared/issue-spec.md)의 "기획서 어디에서 이슈가 나오는가" 표다.

| 점검 항목 | 무엇을 본다 |
| --- | --- |
| **용어 일관성** | 기획서 `## 3. 핵심 개념`의 용어가 도메인 엔티티/컬럼명, 화면 라벨, 이슈 제목에서 다른 이름으로 불리는 곳 |
| **개념 → 도메인** | 핵심 개념 표에 있는데 도메인이 없는 것 / 도메인에는 있는데 기획서 용어 사전에 없는 것 |
| **기능 → 이슈** | `## 4. 핵심 기능` 각 행에 대응하는 에픽이 있는지. 기획에서 **사라진** 기능인데 이슈가 남아 있는지 |
| **비기능 → 이슈** | `## 6. 비기능 요구사항` 각 항목이 이슈로 내려갔는지 (가장 자주 누락된다) |
| **범위 밖 침범** | `## 5. 범위 밖`에 있는데 이슈가 만들어져 있는지 |
| **연동 누락** | `planId`가 빈 이슈(착수 불가), 화면·도메인과 명백히 관련 있는데 `screenId`/`domainId`가 빈 이슈 |
| **끊긴 화면 링크** | 이슈의 `screenId`가 어느 와이어프레임의 `screens`에도 없는 경우 |
| **포지션 분리** | `front`·`back` 라벨이 없는 태스크, 한 태스크에 프론트·백 작업이 섞여 있는 것, 포지션을 뜻하면서 `frontend`·`fe`로 잘못 쓴 것 (issue-spec.md의 "포지션 분리"). ⚠️ **그 밖의 라벨은 건드리지 마라** — `position`(직책 같은 도메인 개념)처럼 이름이 비슷해도 포지션 축이 아니다 |
| **완료 조건 형식** | 완료 조건이 `- [ ]` 체크박스가 아닌 이슈 (진척 추적이 무력화된다) |

### 3) 보고 (기본 산출물)

찾은 차이를 **분류별로, 이슈는 키(`CH-12`)로** 정리해 보여준다. 각 항목에 **무엇을 하면
맞춰지는지**를 한 줄로 붙인다.

- 어긋난 곳이 없으면 "기획과 산출물이 일치합니다"라고만 알리고 **끝낸다**(불필요한 변경 금지).
- 차이가 많으면 **영향이 큰 것부터** 정렬한다: 착수 불가(`planId` 없음) → 누락된 이슈 →
  끊긴 링크 → 용어 불일치 → 형식.

### 4) 반영 — 사용자가 고른 것만

`AskUserQuestion`으로 **무엇을 반영할지 고르게 한다**(복수 선택). 고르지 않은 것은 건드리지 마라.

반영할 때 지키는 것:

- **연동 보강**은 `link_issue(issueId, planId?, screenId?, domainId?)` — 이미 채워진 값은 그대로.
- **누락된 이슈 추가**는 `create_issue`. issue-spec.md 규격을 그대로 따르고 `planId`·
  `applicationId`를 반드시 넣는다.
- **기획에서 사라진 기능의 이슈는 삭제하지 마라.** 사용자에게 알리고 판단을 받는다
  (`delete_issue`는 명시 요청 시에만 — [conventions.md](../ib-shared/conventions.md)).
- **용어 불일치**는 이름을 바꾸는 쪽이 어디인지 물어라. 기획서를 고칠지, 도메인/이슈를 고칠지는
  사용자가 정한다(기획서가 용어의 출처지만, 기획서 쪽이 틀렸을 수도 있다).
- **완료 조건 형식**은 `update_issue(issueId, body=<수정본>)`로 `- [ ]`만 고치고 **다른 본문은
  건드리지 마라.**
- 진행 중(`in_progress`)·완료(`done`) 이슈의 본문은 되도록 손대지 마라. 필요하면 먼저 알린다.

### 5) 마무리 보고

반영한 것 / 사용자가 미룬 것 / 사람이 판단해야 할 것을 나눠 요약한다. 기획이 아직 초안이면
"확정 전까지 이슈를 착수할 수 없다"는 것도 함께 알린다.

## 주의

- **코드를 구현하지 마라.** 산출물은 차이 리포트와 사용자가 승인한 보드 갱신이다.
- 기획서 본문을 고칠 일이 생기면 섹션 안에 녹여 `update_plan`으로 저장한다(하단에 변경 메모를
  쌓지 마라) — [ib-plan](../ib-plan/SKILL.md) 3)절.
- 추측으로 "누락"이라고 단정하지 마라. 애매하면 차이로 보고만 하고 판단은 사용자에게 넘긴다.
